    Architecture¶

    Introduction¶

    TISP (TI Signal Processing) is a software library that strives to abstract away the software and hardware complexity of programming the C7x.

    A typical signal chain is shown in the figure below. Basically, a collection of kernels (nodes) stitched together. A set of these kernels in the signal chain are grouped for DMA (supernode). Typically, in user applications, the complete data needs to be processed by nodes encapsulated inside the supernode before calling the next node in the signal chain. Nodes (kernels) themselves perform compute using data in L2SRAM. Data movement from DDR to L2SRAM (DMA) is accomplished via DRU (Data Routing Unit) available within the C7x.

    Node-Level Abstraction¶

    In order to create a common baseline for kernels from various libraries, TISP first creates a virtual class TISP::VirtualOp. Doing so allows a class to be created for every kernel in a given library that is derived from this base virtual class. Each node can be identified by a unique nodeName and nodeId, which are useful for debugging, profiling, and visualisation purposes.

    Note

    Node-level abstraction is not available for all kernels of a given library. Please refer to the DSP Nodes API page for supported nodes.

    Employing this methodology enables us to string a bunch of nodes together through a custom vector datatype TISP::opVec. An example of the matrix transpose kernel from DSPLIB described as a class TISP::DSPLIB::MatTrans is shown below. Please refer to the DSPLIB documentation for more details about the data structures pertaining to DSPLIB.

    template <typename T>
MatTrans<T>::MatTrans(T         *pX,
                      T         *pY,
                      size_t     width,
                      size_t     height,
                      size_t     inPitchBytes,
                      size_t     outPitchBytes,
                      ErrorCtxt &errorCtx)
    : _pX(pX), _pY(pY)
{

   // Initialize _params with the node parameters
   (void) snprintf(_nodeInfo.params.data(), _nodeInfo.params.size(), "width=%zu,height=%zu", width, height);

   // Input validation checks
   if (pX == nullptr) {
      errorCtx.setNullPointerError("MatTrans constructor", "input pointer pX is null");
   }
   if (pY == nullptr) {
      errorCtx.setNullPointerError("MatTrans constructor", "output pointer pY is null");
   }
   if (width == 0) {
      errorCtx.setInvalidParameterError("MatTrans constructor", "width must be greater than zero");
   }
   if (height == 0) {
      errorCtx.setInvalidParameterError("MatTrans constructor", "height must be greater than zero");
   }

   // Only proceed with initialization if all validation checks passed
   if (errorCtx.isSuccess()) {

      // Initialize bufParams with node input and output buffer parameters. MatTrans
      // swaps width/height between input and output (M x N input -> N x M output).
      _nodeInfo.bufParams.inputDataType     = ElementDType<T>::value;
      _nodeInfo.bufParams.isInputInterleave = 0;
      _nodeInfo.bufParams.widthIn[0]        = width;
      _nodeInfo.bufParams.heightIn[0]       = height;
      _nodeInfo.bufParams.inPitchBytes[0]   = inPitchBytes;

      _nodeInfo.bufParams.outputDataType     = ElementDType<T>::value;
      _nodeInfo.bufParams.isOutputInterleave = 0;
      _nodeInfo.bufParams.widthOut[0]        = height;
      _nodeInfo.bufParams.heightOut[0]       = width;
      _nodeInfo.bufParams.outPitchBytes[0]   = outPitchBytes;
      /***********************************************************************/
      /* Initialize data structures required by DSPLIB_matrTrans from DSPLIB */
      /***********************************************************************/

      DSPLIB_matTransInitArgs kerInitArgs;
      kerInitArgs.dimX      = width;
      kerInitArgs.dimY      = height;
      kerInitArgs.funcStyle = DSPLIB_FUNCTION_OPTIMIZED;

      _handle = make_unique_handle<char>(DSPLIB_matTrans_getHandleSize(&kerInitArgs));

      if (!_handle) {
         errorCtx.setMemoryError("MatTrans constructor", "failed to allocate matTrans handle");
      }

      DSPLIB_bufParams2D_t bufParamsIn;
      DSPLIB_bufParams2D_t bufParamsOut;

      bufParamsIn.data_type = DSPLIB_element_dType<T>::value;
      bufParamsIn.dim_x     = static_cast<uint32_t>(width);
      bufParamsIn.dim_y     = static_cast<uint32_t>(height);
      bufParamsIn.stride_y  = static_cast<int32_t>(inPitchBytes);

      bufParamsOut.data_type = DSPLIB_element_dType<T>::value;
      bufParamsOut.dim_x     = static_cast<uint32_t>(height);
      bufParamsOut.dim_y     = static_cast<uint32_t>(width);
      bufParamsOut.stride_y  = static_cast<int32_t>(outPitchBytes);

      if (errorCtx.isSuccess()) {
         DSPLIB_STATUS checkRet =
             DSPLIB_matTrans_init_checkParams(_handle.get(), &bufParamsIn, &bufParamsOut, &kerInitArgs);
         errorCtx.remapXLIBError(checkRet, "DSPLIB_matTrans_init_checkParams");

         /******************************************************************************/
         /* Call init function from DSPLIB to for matrix transpose to set SE/SA params */
         /******************************************************************************/

         if (errorCtx.isSuccess()) {
            DSPLIB_STATUS initRet = DSPLIB_matTrans_init(_handle.get(), &bufParamsIn, &bufParamsOut, &kerInitArgs);
            errorCtx.remapXLIBError(initRet, "DSPLIB_matTrans_init");
         }
      }
   }
}

    Connecting and executing supernodes is also similar to nodes. Each supernode keeps track of the number of blocks it processes, which is useful for performance analysis and profiling.

    L2SRAM Memory Management¶

    On TI C7x DSPs, L2SRAM is the fastest on-chip memory (zero wait states), while DDR access incurs approximately 150 cycle latency. TISP manages L2SRAM allocation through a simple mechanism: you give it a byte array, and it hands back aligned chunks from that array on demand. No operating system heap, no fragmentation — just a pointer that moves forward through a fixed-size buffer.

    The class that implements this is TISP::BumpAllocator. It is compliant with MISRA C++:2023 Rule 21.6.2, AUTOSAR A18-5-10, and SEI CERT MEM54-CPP.

    Bump Allocator¶

    Think of TISP::BumpAllocator like a roll of tape. You pull off what you need (allocate), and the roll gets shorter. You can rewind the whole roll at once (reset), but you cannot put a piece back in the middle.

    Each allocation returns a smart pointer (TISP::ArenaPtr) that automatically releases its memory when it goes out of scope. You choose the alignment you need — 32-byte, 64-byte, or custom — depending on what the DSP vector unit requires.

    // Step 1: Declare a byte array in L2SRAM (the "roll of tape")
__attribute__((section(".l2sramData"), aligned(128))) uint8_t myArena[64 * 1024];

// Step 2: Hand it to the allocator
TISP::BumpAllocator alloc(myArena, sizeof(myArena));

// Step 3: Pull off what you need
TISP::ArenaPtr<float> buf = alloc.allocate64ByteAligned<float>(1024);

    Arena Ownership Model¶

    TISP uses two separate arenas (byte arrays). Who owns each one determines who is responsible for sizing and declaring it:

    Arena

    Who owns it?

    What is it for?

    Node arena

    Your application

    You declare the byte array and decide how big it is based on your signal chain.

    Twiddle arena

    TISP library

    A fixed 32 KB internal array used by FFT nodes. You never touch it directly.

    The library provides the allocator class (TISP::BumpAllocator). Your application provides both the node arena memory and the twiddle arena memory — you declare the backing arrays and choose their section placement at link time. The function TISP::twiddleAllocator() returns a reference to the allocator that FFT nodes use internally.

    On target hardware, the twiddle arena is typically placed in L2SRAM (e.g. .tisp_twiddle_arena section) for zero-wait-state access. On a PC (host emulation), the same externally-provided buffer compiles as a plain aligned array — same API, same behaviour, no hardware dependency.

    Twiddle Factor Arena¶

    FFT algorithms need precomputed trigonometric constants called “twiddle factors.” These are purely a function of the FFT size — compute them once, reuse them on every frame. TISP handles this internally so the application does not need to know anything about twiddle factor allocation.

    When you create an FFT node (e.g., FFT1dBatched), the constructor allocates twiddle factors from the library-owned twiddle arena behind the scenes:

    // Inside FFT1dBatched constructor (internal -- app never calls this directly):
_pW = twiddleAllocator().allocate64ByteAligned<T>(_numPoints * 2);
tw_gen();  // Fill in the twiddle factor values

    The TISP::twiddleAllocator() function is a one-liner that returns a reference to a pre-existing allocator. Here is the complete implementation — there is nothing hidden:

    // src/common/TISP_bump_allocator.cpp

// The backing array is declared by the application (extern linkage).
// See test/common/TISP_app_arena_default_config.cpp for the default:
//   __attribute__((section(".tisp_twiddle_arena"), aligned(64)))
//   uint8_t tisp_twiddleArenaBuffer[32U * 1024U];
extern uint8_t tisp_twiddleArenaBuffer[];
extern const size_t tisp_twiddleArenaSize;

// Allocator that manages the byte array above -- created once at startup
static BumpAllocator twiddleAllocatorInstance(
    tisp_twiddleArenaBuffer, tisp_twiddleArenaSize, kTwiddleAlignment);

// Returns a reference to the allocator above -- this is the entire function
BumpAllocator &TISP::twiddleAllocator() { return twiddleAllocatorInstance; }

    Why this design?

    • Always available: the byte array and allocator exist for the entire program lifetime, so FFT twiddle factors are always valid — no use-after-free.

    • No external dependencies: pure C++14 — no TI SDK heap calls, no OS allocator, no fragmentation risk.

    • Zero cost at runtime: twiddle factors are accessed as plain pointers during signal processing. The smart-pointer bookkeeping only runs when you create or destroy an FFT node, not on every frame.

    Performance Profiling¶

    TISP includes a comprehensive profiling system through the NodeProfiler class (global scope) that allows you to measure and analyse the performance of both individual nodes and supernodes. The profiler captures cycle counts for each node execution and provides detailed analytics for performance optimisation.

    Key profiling features include:

    • Cycle count measurement for individual nodes and supernodes

    • Node identification via nodeName and nodeId for easy tracking

    • Block count tracking for supernodes to analyse per-block performance

    • JSON output for detailed performance analysis

    • Excel report generation via the json_to_xlsx_converter.py tool

    The profiling system helps identify performance bottlenecks and provides insights into the efficiency of supernode execution by comparing actual cycles with theoretical cycles based on the sum of node cycles multiplied by the number of blocks processed.

   if (errorCtx.isSuccess()) {

          BLOCK_SIZE, NUM_CHANNELS_OUT, NUM_CHANNELS * sizeof(float), NUM_CHANNELS_OUT * sizeof(float), true, "Router",
          8, errorCtx);
      if (errorCtx.isSuccess()) {
         myOpVec->push_back(std::move(k8));
      }
      else {
         printf("Error: Failed to create Node 8: %s\n", errorCtx.getMessage());
      }
   }

   if (errorCtx.isSuccess()) {
      auto k9 = TISP::make_unique_node<TISP::AUDIOLIB::TypeConversion<float, int32_t>>(
          pOutRouter, pFloatToInt, NUM_CHANNELS_OUT, BLOCK_SIZE, (NUM_CHANNELS_OUT * sizeof(float)),
          (NUM_CHANNELS_OUT * sizeof(int32_t)), false, "TyperConversion: FloatToInt", 9, errorCtx);
      if (errorCtx.isSuccess()) {
         myOpVec->push_back(std::move(k9));
      }
      else {
         printf("Error: Failed to create Node 9: %s\n", errorCtx.getMessage());
      }
   }

   if (errorCtx.isSuccess()) {
      myGraph = myOpVec;
      TISP::printArenaStats();
   }
   else {
      delete myOpVec;
   }

   return myGraph;
}

   uint32_t *pOut = (uint32_t *) FLOAT_TO_INT_ADDR;

   size_t       length  = myOpVec->size();

   TISP::SetAddr_t addr;

   for (auto k = 0; k < (NUM_SAMPLES) / (BLOCK_SIZE); k++) {

      // begin poor man's DMA: memcopy a block
      for (auto j = 0; j < BLOCK_SIZE; j++) {
         for (auto i = 0; i < NUM_CHANNELS; i++) {
            pIn[j * NUM_CHANNELS + i] = inputSignalCase5[i + j * NUM_CHANNELS + k * BLOCK_SIZE * NUM_CHANNELS];
         }
      }
      // end poor man's DMA
